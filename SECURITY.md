Кто получит service_role-ключ, получит и ключи хранилищ.

### Ротация — по шагам

Понимать до начала: `get-day` выдаёт presigned-ссылки с `X-Amz-Expires=3600`, подписанные

прямо сейчас. Поэтому старый ключ удаляется **через час после** переключения, не раньше.

1. Панель Timeweb Cloud → Облачное хранилище → бакет `irenabio-audio` → ключи доступа S3 →
   создать новую пару. Старую не трогать.
2. Обновить обе строки:
   ```sql
   update public.app_config set value = '<новый access>' where name = 'TIMEWEB_ACCESS_KEY';
   update public.app_config set value = '<новый secret>' where name = 'TIMEWEB_SECRET_KEY';
   ```
   через `npx supabase db query --linked -f rotate.sql`. Файл после применения удалить.
3. Проверка: открыть день с аудио с российского IP либо дёрнуть `get-day` с
   `force_host=timeweb`, убедиться что presigned-ссылка отдаёт 200.
4. Отдельно проверить загрузку через `content-admin` — он читает те же ключи.
5. Подождать час. Удалить старую пару в панели.
6. Повторить проверку из п.3.

**MinIO (Алматы)**

2. Создать новый access key / service account, политику ограничить бакетом `audio`.

## 2. Supabase Auth

**Лимиты на вход есть, встроенные, платформенные.** Проверено живой пробой по несуществующим
адресам (реальные аккаунты не задеты):

```
POST /auth/v1/token?grant_type=password   x40
-> 400 x35, затем
   429 {"code":429,"error_code":"over_request_rate_limit","msg":"Request rate limit reached"}
```

Это дефолтный GoTrue-лимит на `/auth/v1/token` — порядка 30 запросов за 5 минут с небольшим
бёрстом. Что про него важно:

- Лимит **по IP, не по аккаунту.** Блокировки аккаунта после N неудач нет — такого механизма
  в Supabase нет в принципе. Атака с пула прокси перебирает пароль конкретной женщины
  без ограничений.
- Счётчика неудачных входов нет, алёрта нет, уведомления женщине «кто-то пытался войти» нет.
- Ответ на несуществующий email и на неверный пароль одинаковый — энумерации нет, это хорошо.

**Что настраивается:** Dashboard → Authentication → Rate Limits, значения по каждому эндпоинту
(token, signup, verify, recover). Понизить можно, превратить в per-account lockout — нет.

**Публичный конфиг** (`/auth/v1/settings`, читается кем угодно с publishable-ключом):

```
disable_signup: false      mailer_autoconfirm: true
email: true                passkeys_enabled: false
всё остальное (google/apple/phone/saml/...): false
```

Два неприятных следствия:

- **Регистрация открыта всем.** Сам по себе аккаунт ничего не даёт (доступ считается через
  `account_identities` → `subscriptions`), но это сырьё для раздела 4.
- **`mailer_autoconfirm: true` — письма подтверждения не шлются вообще.** Владение почтой
  никогда не доказывается. Решение осознанное (аудитория РФ/РБ, письма не доходят), но именно
  оно делает номер заказа единственным доказательством и переводит раздел 4 из «неаккуратно»
  в «дыра».

**Защита от утёкших паролей (HIBP) — проверить не удалось.** Платформенная настройка,
её не отдаёт ни CLI, ни публичный `/settings`; Management API недоступен (токен CLI лежит
в Windows Credential Manager). По умолчанию в Supabase выключена. См. чек-лист наверху.

## 3. admin-grant и mint-app-token

### admin-grant — ограничений частоты нет, подтверждено

20 запросов подряд с неверным токеном (`код:секунды`):

```
403:0.55 403:0.51 403:0.13 403:0.15 403:0.13 403:0.16 403:0.13 403:0.15 403:0.14 403:0.14
403:0.14 403:0.13 403:0.13 403:0.19 403:0.13 403:0.18 403:0.13 403:0.12 403:0.15 403:0.13
```

- **Задержки нет.** ~135 мс на попытку, время не растёт. Первые два — холодный старт.
- **Блокировки нет.** Ни по IP, ни глобально. In-memory rate-limit, который есть
  у `resolve-paid-order` / `reset-password` / `claim-account`, в `admin-grant` не добавлен.
- **Логов о промахах нет.** Ветка `forbidden` возвращает 403 молча, без `console.error`.
  В логах платформы останется счётчик 403-х, и то на сутки (Free) / неделю (Pro). Алёрта нет.
- Функция публична полностью: `verify_jwt=false`, CORS отражает любой Origin, `apikey`
  не требуется. Дёргается голым курлом откуда угодно.
- Сравнение `body?.token !== ADMIN_GRANT_TOKEN` не константное по времени. По сети
  неэксплуатируемо, упомянуто для полноты.

**Но приоритет меняет вот что.** Соседний `ADMIN_CONTENT_TOKEN` в `.env.local` — 64
hex-символа, 256 бит энтропии. Если `ADMIN_GRANT_TOKEN` сгенерирован так же (он из той же
серии, июнь 2026), **перебор невозможен физически.** Отсутствие rate-limit тогда не дыра,
а неопрятность: мешает заметить атаку, а не остановить её. Поэтому первый пункт чек-листа
наверху — проверить токен.

**Реальный вектор здесь не перебор, а утечка целиком.** Токен лежит открытым текстом
в `localStorage` браузера Ирены на `ir-grant.vercel.app` (ключ `ir_admin_grant_token`),
вводится руками, живёт вечно, не привязан ни к IP, ни к сроку. Вредоносное расширение,
чужой доступ к ноутбуку, скриншот формы — и у постороннего вечная кнопка «выдать себе
доступ на 3650 дней».

**То же самое, слово в слово, относится к `content-admin`:** тот же паттерн токена в теле,
тот же CORS `*`, тот же ноль rate-limit. Через него правится контент и подписываются
загрузки в бакеты.

### mint-app-token — ограничений нет, но они там почти не нужны

Гейт — валидная Supabase-сессия плюс живая подписка. Без чужого access-токена перебирать
нечего: сессия либо есть, либо нет. Функция ничего не пишет в БД.

### Общее замечание по Origin-фильтрам

В `mint-app-token`, `verify-app-token`, `get-day`, `get-home`, `resolve-paid-order`,
`attach-web-identity`, `claim-account`, `reset-password`:

```js
const ALLOWED_ORIGIN_PATTERNS = [ /^https:\/\/app\.irenabio\.com$/, /\.github\.io$/, ... ];
```

`/\.github\.io$/` проверяется против `url.host` без якоря начала — проходит **любой** сайт
на GitHub Pages, `evil.github.io` в том числе. Токен так не украсть (чужой origin не читает
ваш localStorage), но CSRF-барьер снят. Правка: `/^https:\/\/vladlen00\.github\.io$/`.

И главное: **Origin вообще не барьер против не-браузерного клиента.**
`curl -H "Origin: https://vladlen00.github.io"` проходит везде. Origin защищает только
от чужой веб-страницы. См. находку №2.

## 4. Ссылка из ir-grant

**Хуже, чем «не сгорает».** Ссылка `?paid=1&order=manual_<32hex>` — не приглашение задать
первый пароль, а **бессрочный универсальный ключ от аккаунта**, работающий в обе стороны.

Кто угодно, открыв ссылку, может:

1. `POST resolve-paid-order {orderReference}` → получить **email женщины**. Заказ помечен
   `consumed_at` сразу при создании, значит проверка «оплачен» проходит всегда.
2. Дальше две ветки, обе ведут внутрь:
   - аккаунта ещё нет → `claim-account {email, order, password}` создаёт пользователя
     с `email_confirm` и привязывает к её `person_id`;
   - аккаунт **уже есть** → `reset-password {email, order, password}` **меняет пароль
     существующего аккаунта** через GoTrue Admin.
3. Войти. Внутри — подписка, вся история Подружки, чек-ины, данные анализов.

Почта не нужна ни на одном шаге (`mailer_autoconfirm: true`). Владелица ящика не получит
ни одного письма и не узнает.

**Это не только про manual-ссылки.** Модель одинаковая для всех оплаченных заказов:
`wfp_*` и Lava-UUID тоже дают `reset-password`. Номер заказа виден в адресной строке после
оплаты, оседает в истории браузера, в чеке платёжки, в пересланном скриншоте.

Состояние базы на 2026-08-19:

```sql
select count(*) filter (where consumed_at is not null) as consumed_orders,
       count(*) filter (where consumed_at is not null
                        and order_reference like 'manual_%') as manual_links,
       count(*) as total_orders
from public.pending_checkouts;

-> consumed_orders: 12, manual_links: 4, total_orders: 35
```

**12 действующих бессрочных ключей от аккаунтов.** С каждой продажей плюс один, навсегда.

### Как дёшево добавить срок жизни

Место ровно одно. В `pending_checkouts` добавить `expires_at timestamptz`, в `admin-grant`
при создании фиктивного заказа ставить `now() + interval '7 days'`, и в четырёх читателях
(`resolve-paid-order`, `attach-web-identity`, `reset-password`, `claim-account`) дописать
в существующий PostgREST-фильтр:

```
&or=(expires_at.is.null,expires_at.gt.now())
```

`NULL` = без срока, поэтому все 35 существующих заказов работают байт-в-байт, миграция
данных не нужна. Новые manual-ссылки живут неделю.

Отдельно и почти бесплатно — сделать `reset-password` **одноразовым**: после успешной смены
пароля ставить заказу `expires_at = now()`. Тогда номер заказа перестаёт быть вечным
мастер-ключом, оставаясь одноразовой страховкой «оплатила, не вижу доступа». Это снимает
большую часть риска и со старых `wfp_*`.

Телеграм-дверь не задета: ветка чисто веб.

## 6. Находки по цене отказа

### №1. Приватная переписка 458 женщин читается публичным ключом из бандла

Самое дорогое. Воспроизведено:

```
GET /rest/v1/chat_history?select=*&limit=1   apikey: <publishable из бандла>
-> HTTP 206, Content-Range: 0-0/14271

GET /rest/v1/checkins?select=*&limit=1
-> HTTP 206, Content-Range: 0-0/3950
```

**14 271 сообщение от 458 женщин и 3 950 чек-инов от 676 женщин** доступны любому,
кто откроет исходник страницы и скопирует ключ. Причина — две политики:

```
chat_history  anon_full_access_chat_history  PERMISSIVE {anon} ALL  USING true  CHECK true
checkins      anon_full_access_checkins      PERMISSIVE {anon} ALL  USING true  CHECK true
```

плюс сохранившиеся гранты `anon: SELECT, INSERT` (у `checkins` ещё и `UPDATE`).
`DELETE` снят — это единственное, что делали.

Содержимое — гормоны, цикл, вес, сон, симптомы, всё то, что женщина писала «Подружке»,
считая разговор частным. Плюс `user_id`, по которым эти данные склеиваются между собой.
По смыслу это медицинские данные. Цена отказа: доверие аудитории и статья про персональные
данные, а не «неудобство».

**`tracker-data` уже написан именно чтобы это закрыть** — в его шапке это прямым текстом.
Этап B сделан наполовину: **чтение** идёт через функцию, но с фолбэком на прямой anon-запрос
(`biohack/src/App.js:196`, `:202`, `:219`, `:225`), а **запись** (`chat_history` insert
`src/App.js:100`, `checkins` upsert `:173`) до сих пор идёт напрямую. Поэтому гранты
и не сняты. Работа на 80% сделана, не хватает последнего шага.

**Остальные 30 таблиц проверены поимённо:** RLS включён, политик ноль, читается пусто.
`persons`, `subscriptions`, `pending_checkouts`, `day_blocks` — все отдают `[]`.
Но у 27 из них у `anon` висят **полные гранты** (`SELECT/INSERT/UPDATE/DELETE`),
и единственное, что стоит между ними и интернетом, — RLS без политик. Одна случайно
добавленная permissive-политика или один `disable row level security` — и таблица мгновенно
публична. Именно так и появились эти две.

### №2. Ключ Anthropic жжётся посторонними без ограничений

`chat` берёт `userId` **из тела запроса** (`chat/index.ts:842`) и никак его не проверяет.
Единственный гейт — заголовок `Origin`, а allowlist там `/\.vercel\.app$/` — любой поддомен
Vercel. Проверено живьём:

```
без Origin                                        -> 403
Origin: https://totally-not-mine-12345.vercel.app -> 400 "Invalid messages"  (гейт пройден)
Origin: https://t.me                              -> 400                     (гейт пройден)
```

400 — это уже **после** проверки Origin, на валидации тела. То есть заголовок, который клиент
пишет сам, — вся защита.

Дневной лимит 5 запросов считается **по `userId` из тела**. Меняешь строку — счётчик
обнуляется. Итого: любой человек с курлом обращается к вашему `ANTHROPIC_API_KEY` бесконечно.
При расходе ~$95 за 41 день на 208 подписчиц скрипт нагонит четырёхзначный счёт за ночь,
и первым сигналом будет письмо от Anthropic, а не алёрт.

Плюс `ADMIN_USER_IDS` захардкожены открытым списком в коде функции (`chat/index.ts:519`) —
кто их узнает, обходит лимит вообще.

Починка та же, что у `tracker-data`: требовать наш JWT (`verify-access` для Телеграма,
`mint-app-token` для веба), брать `userId` из проверенного `sub`, а не из тела.
Механизм уже написан и работает, надо применить.

### №3. Любой мог переписать контент дня публичным ключом — ЗАКРЫТО 2026-08-19

`admin_upsert_day` — `SECURITY DEFINER` с `EXECUTE` у `PUBLIC`. Единственное, что стояло
на пути, — знание UUID спринта, а он утекает любой подписчице в ответе `get-home`, то есть
достаточно одной подписки за 11 EUR. Функция делает `delete from day_blocks where day_id = ...`
и вставляет что прислали: контент дня можно было **стереть или подменить** для всех ~900
женщин. Это не только вандализм, но и канал для фишинга по вашей аудитории от вашего имени.

Соседние `apply_manual_grant`, `apply_wayforpay_payment`, `apply_lava_payment` и родственные
тоже имели `EXECUTE` у `PUBLIC`. Они `SECURITY INVOKER` — упирались в RLS на `subscriptions`
и падали. Опасности не было, но это защита соседа, а не собственный замок.

**Тонкость, важная при похожих правках в будущем:** в ACL стояло `=X/postgres` — пустой
grantee означает `PUBLIC`. Отзыв только у `anon`/`authenticated` был бы no-op, право осталось
бы через `PUBLIC`. В миграции поэтому `from public, anon, authenticated`.

Результат и проверка — в разделе «Что уже закрыто».

## Задача 6: Basic Auth на ir-ops, по шагам

`ir-ops` деплоится через Vercel CLI из папки `Desktop/ir-ops` (своего git-репозитория у неё
нет, есть `.vercel/project.json` с `projectName: ir-ops-29c624`).

**1. Положить файл.** Скопировать `Desktop/ir-grant/middleware.js` в
`Desktop/ir-ops/middleware.js` без единой правки. Файл должен лежать **в корне папки**,
рядом с `index.html` — без `config.matcher` он применяется ко всем путям, включая `upload.html`.

**2. Завести переменные в дашборде Vercel.**
Открыть vercel.com → проект **`ir-ops-29c624`** (не `ir-grant`) → вкладка **Settings** →
в левом меню раздел **Environments** → выбрать **Production** → внутри блок с переменными →
**Add** / **Create new**. Добавить две:

| Key | Value |
|---|---|
| `GRANT_USER` | логин, любой |
| `GRANT_PASS` | пароль, **новый, не тот же что у `ir-grant`** |

Имена именно `GRANT_USER` / `GRANT_PASS` — их читает скопированный `middleware.js`,
переименовывать не нужно. Переменные у каждого проекта свои, с `ir-grant` они не пересекаются,
даже если названия совпадают.

Если планируете заходить и на preview-деплои — повторить те же две переменные
для окружения **Preview**.

**3. Передеплоить.** Переменные окружения **не применяются к уже выкаченным деплоям**,
нужен новый. Из папки `Desktop/ir-ops`:

```
vercel --prod
```

**4. Проверить.** Должно стать 401 на обоих адресах:

```bash
curl -s -o /dev/null -w "%{http_code}\n" https://ir-ops-29c624.vercel.app/
curl -s -o /dev/null -w "%{http_code}\n" https://ir-ops-29c624.vercel.app/upload.html
```

Оба ответа — `401`. Если хоть один `200`, значит либо `middleware.js` не в корне, либо деплой
прошёл до добавления переменных. Различить просто: `middleware.js` при пустых
`GRANT_USER`/`GRANT_PASS` отдаёт 401 **всегда**, так что `200` означает, что middleware
не подхватился вовсе — смотрите, где лежит файл.

**5. Открыть в браузере** — браузер спросит логин и пароль. Сохранить их в менеджер паролей.
